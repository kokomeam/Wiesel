## Executive summary

The codebase is a strong host for TUTOR-1: almost every mechanism the directive requires has a battle-tested precedent to extend — a subagent primitive with tool allow-sets and structured verdicts, an SSE token-streaming pipeline, an append-only idempotent event stream with a codified extension recipe, immutable versioned snapshots with verbatim node-id stability, an Accept/Reject rail with a written extension doctrine, a versioned-update + typed-409 write pattern, per-course settings rows, definer-RPC RLS hygiene at four grant tiers, and an in-house pure-SVG diagram/layout stack that seeds the graph editor.

However, **seven directive assumptions are contradicted by the tree** and need explicit resolution before Wave 1: (1) **Inngest does not exist** — all timed work is pg_cron + CRON_SECRET drain routes + one Vercel cron; (2) there is **no universal call-dispatch layer** — the 2-call semaphore is opt-in at 5 call sites, per-serverless-instance, and most interactive model calls bypass it; (3) **`previous_response_id` chaining is absent** and foreground calls run `store:false` by documented design; (4) the platform's standing privacy posture is the **opposite** of aggregate-only — creators today read individual learner progress, attempts, emails, flags, and raw event timelines; (5) the Accept/Reject rail's Reject path is **hard-coupled to CourseDocument** — a concept-graph change-set would accept but throw on reject without extension; (6) the comms pipeline is **structurally learner-recipient-only** — no platform→creator email/digest path exists; (7) **graded assessments don't exist** — quizzes are low-stakes by explicit design. All seven have concrete, codebase-native resolutions proposed in the risk register.

## 1. `runSubagent` primitive, agent loop, and streaming

### 1.1 The primitive

- **Signature:** `runSubagent<T>(p: RunSubagentParams<T>): Promise<SubagentResult<T>>` — `lib/ai/subagent.ts:213`. Params (`:170-192`): a shared `LoopContext c` (model already semaphore-wrapped, ONE `CallBudget` by reference), `role`, `systemPrompt`, `context` (developer context string), `userMessage`, `outputSchema`/`outputName` (Zod → strict JSON schema), optional `tools?: ReadonlySet<string>`, `doc`, `lessonId`, `maxTurns` (default 6), `tokenBudget`. Result (`:194-207`): `{ok, data, truncated, usage: PhaseUsage, toolCalls, transcript: {tool, summary}[], doc, docMutated, error}`.
- **Two modes** (`:227-254`, `:274-283`): with `tools`, it runs `runConversationLoop` (`systemOverride`, `allowedToolNames`, `persist:false`, `deferFinalize:true`, `callLabel: maintenance:{role}`) then a one-shot structured **verdict**; without `tools` it goes straight to the verdict (the Comms subagent pattern — `lib/ai/maintenance.ts:577-586`).
- **`runStructuredCall`** (`lib/ai/subagent.ts:111-162`): one strict `json_schema` call (`toStrictJsonSchema`), exactly one re-ask on parse failure, no tools/streaming/persistence. ⚠ It builds `ModelTurnParams` **without** `model`/`effort`/`timeoutMs`/`maxRetries` (`:123-131`) — it cannot express per-job model routing or a hard deadline today; TUTOR-1 must extend its options additively before routing tutor jobs through it.
- **Budgets:** `CallBudget {remaining}` is shared by reference through `LoopContext` (`lib/ai/agentLoop.ts:60-62`, decremented per turn at `:600`); `tokenBudget.remaining` is decremented by `inputTokens + outputTokens` after the loop and after the verdict (`subagent.ts:248, 282`). Note: in the Responses API `output_tokens` **includes** reasoning tokens (`usage.output_tokens_details.reasoning_tokens` is a breakdown, extracted at `lib/ai/providers/openai.ts:232-239`), so reasoning IS budget-counted; `PhaseUsage.reasoningTokens` exists for telemetry only.
- **Graceful truncation:** budget pre-check returns `{ok:false, truncated:true, error:"budget_exhausted"}` (`subagent.ts:222-224`); if the call budget dies mid-run, the LAST call is spent on the verdict over whatever was gathered (`:256-261`); token exhaustion post-verdict flags `truncated` (`:283`).
- **`persist:false`** writes NOTHING to `conversations`/`messages` and loads no history (`agentLoop.ts:159-162`, `~:484-491`); the replayable trace is the `transcript` array, persisted by the orchestrator into `agent_runs.report`.
- **Error semantics:** `finishReason === "error"` breaks the loop immediately (`agentLoop.ts:647`); errors are categorized `transport_timeout | model_error | transport` (`lib/ai/providers/openai.ts:207-217` — a deadline abort is never mis-parsed as bad JSON); the structured call surfaces `errorKind` (`subagent.ts:151-152`).

### 1.2 Orchestrator registration precedents

- **Maintenance** (the "Course" orchestrator): Analyst runs with `ANALYST_TOOL_NAMES` (analytics + read tools — `lib/ai/tools/index.ts:83-86`), then Remediation runs **sequentially** over the shared in-memory doc (`lib/ai/maintenance.ts:455-470`) with `REMEDIATION_TOOL_NAMES` (`tools/index.ts:91-95`) while Comms drafts run **concurrently** (`maintenance.ts:620` — no doc mutation). Tool allow-sets filter the cached registry at `agentLoop.ts:483` (`getToolDefinitions().filter(t => allowed.has(t.name))`; registry assembly `lib/ai/tools/index.ts:18-25, 102-110`). Impure capabilities are **injected on ToolContext** (`agentLoop.ts:320-324` — `analytics?: AnalyticsToolContext`; the `visuals` precedent) — the pattern for the tutor's `generate_practice` capability.
- **Marketing** does NOT use `runSubagent` — it has its own loop (`lib/marketing/agent/loop.ts:53-191`) with gate-routed tools and a hard 120s per-turn deadline (`:85-90`). TUTOR-1's mandate to use `runSubagent` is satisfiable; marketing is the precedent that per-turn `timeoutMs` is required for interactive loops (the bare agent loop passes **no** `timeoutMs` today — `agentLoop.ts:602`).

### 1.3 Streaming (the learner sidebar's transport)

- Token deltas flow end-to-end **today**: provider emits `text_delta` per streamed token (`lib/ai/providers/openai.ts:448-450`) → the loop re-emits `assistant_delta` (`agentLoop.ts:602-611`) → `encodeSSE` frames (`lib/ai/events.ts:58, 121-123`) → the SSE route enqueues on a `ReadableStream` (`app/api/ai/agent/route.ts:78-88`; `req.signal` threaded at `:102`) → the client reads with fetch+reader, batches deltas, settles on `assistant_message` (`components/editor/agent/useAgentStream.ts:64-74, 123-129, 144-171`). No auto-reconnect exists (`:166-168, 197-204`) — errors render and the user retries.
- `runSubagent`'s emit wrapper **passes every event through** to the orchestrator's emit (`subagent.ts:232-237`) — so streaming a subagent-style run to a NEW learner-facing SSE route works with zero changes to the primitive: hand it an emit that enqueues to the route's `ReadableStream`.
- **The genuine gaps** for the tutor runtime: (a) a learner-facing SSE route (all of `/api/ai/*` is creator-principal; `/api/learn/*` is non-streaming) — build `/api/learn/tutor` on the exact `route.ts` pattern with `requireUser` + enrollment gate; (b) turn persistence — `persist:false` means streamed tutor turns are never stored; tutor threads need **their own tables** with explicit turn writes (see §10 — the existing `conversations`/`messages` have no owner column and author-only RLS, and 1:1 reuse was evaluated and rejected); (c) a queue-state event member for the "thinking / N ahead of you" state (`AgentEvent` has no such member — `lib/ai/events.ts:20-116`; the additive-`maintenance`-member precedent applies); (d) per-turn `timeoutMs` on loop options.
- **History replay:** `lib/ai/conversations.ts` (threads per (course, lesson), full-history replay each turn; `:25-60, 62-87, 114-131`) + bounded `historyPolicy` (`lib/ai/historyPolicy.ts:42-55`; edit policy `:64-73`; scoped GENERATE loads zero history `:136-146`; tool-result compaction `:85-107`) — the direct precedent for the tutor's L4 conversation layer if/until `previous_response_id` chaining lands (§8).

## 2. Concurrency dispatcher

### 2.1 What exists

- The ceiling is a hand-rolled module-level `Semaphore` (`lib/ai/subagent.ts:34-60`), singleton sized by `MAINTENANCE_MAX_CONCURRENT_MODEL_CALLS` (default 2, floor 1 — `:63-65`; `.env.example:117`), applied via the **`withSemaphore` ModelClient decorator** which caps `runTurn` only — `generateImage`/`inspectImage` pass through unwrapped (`:70-87`).
- **The injectable seam already exists:** `withSemaphore(base, semaphore = modelCallSemaphore)` accepts a second `Semaphore` (`:70-73`) — every production call site currently defaults it. This is the pool-keying point.
- **Coverage is opt-in, not global.** `withSemaphore` appears in exactly 5 files (grep): its definition, `lib/ai/maintenance.ts:375` (wraps the run's shared context — all three subagents share it), `lib/marketing/social/generate.ts:281` + `lib/marketing/social/service.ts:76-79,491,533`, and the verify script. **Bypassing it:** the studio content agent (`app/api/ai/agent/route.ts:75,92`), plan/confirm/visual routes, the marketing agent chat (`lib/marketing/agent/loop.ts:93`), email `llmGenerate.ts:129`, the intent classifier (`lib/ai/intent.ts:116`), and even social voice derivation (`generate.ts:106` passes the RAW model before wrapping at `:281`). The module's own doc-comment overstates its scope (`subagent.ts:10-13`).
- **Known defects to fix during the pool rework:** wake order is FIFO (`shift()`, `:56`) but a synchronous acquirer can **barge** in the release→wake microtask gap, and the woken waiter's unconditional increment (`:49`) can transiently exceed `max` (verified against `:44-58`; the verify suite asserts the cap but never wake ORDER — `scripts/verify-maintenance.ts:95-123`). `acquire()` is **not abort-aware** and has no wait deadline (`:44-50`) — an abandoned SSE request keeps its slot and still runs. Queue depth is invisible (only `inFlight` is public — `:40-42`).
- **Per-instance semantics:** the semaphore is Node-module state; the deployment target is Vercel (`vercel.json:2-6`, `next.config.ts:4-6`). Any pool is per-serverless-instance — N instances × `learner_pool(8)` = platform ceiling 8N, and no route exports `maxDuration` (grep: 0 hits), so queue-wait must fit the platform's default function duration.
- **Deadline layer to reuse:** per-call `params.timeoutMs` → `withTimeoutSignal` AbortController (`lib/ai/providers/openai.ts:142-172, 342-347`; the SDK's own timeout is unreliable under proxied undici, `:335-341`). Existing budgets: marketing turns 120s (`loop.ts:90`), plans/social/follow-up 180s (`modelConfig.ts:168`; `social/constants.ts:203`; `(app)/marketing/actions.ts:394,412`), background poll 300s. Convention pairs `timeoutMs` with a low `maxRetries` (`modelClient.ts:95`; `phases.ts:218,224`; `social/generate.ts:132`) — omitting it inherits `DEFAULT_MAX_RETRIES = 5` under the deadline.

### 2.2 Change surface for per-principal pools (directive §0.2)

1. Pool registry beside `modelCallSemaphore` in `subagent.ts`: `poolFor("creator" | "learner")` → dedicated `Semaphore`s sized by new envs `AI_CREATOR_POOL_MAX` (default 2) / `AI_LEARNER_POOL_MAX` (default 8); keep `modelCallSemaphore` as the creator-pool alias so all 5 existing call sites stay behavior-identical.
2. Fix the Semaphore during generalization: explicit **slot transfer** on release (removes barging + over-admission), `acquire(signal?: AbortSignal)` (reject-and-remove waiter on abort; `withSemaphore` already receives `params.signal`), public `queued` getter, wake-order + abort assertions added to `verify-maintenance.ts`.
3. Queue visibility: one additive `AgentEvent` member (e.g. `{type:"queued", position}`) emitted by the tutor loop around `acquire()` — AC-T0.2's "user-visible thinking state".
4. Cost-event emission belongs in this same decorator (single interception point for `result.usage`) — see §3.4.
5. **Decision required** ([R-2](#r-2)): the directive says pools "replace the global ceiling" in "the ONE existing call-dispatch layer" — no such universal layer exists. Recommended scope: tutor traffic joins `learner_pool`; maintenance/social stay on the creator pool alias; existing *interactive creator* surfaces (studio agent, marketing chat) stay unpooled in TUTOR-1 (retrofitting them changes shipped latency behavior and belongs to a separate decision).

## 5. Accept/Reject rail — state and extension for concept-graph artifacts

### 5.1 What the rail is today

- Two tables: `change_sets` (pending→accepted|rejected — `20260615010000:49-60`) + `change_set_items` (whole-node before/after jsonb snapshots, `op ∈ create|update|delete`, `block_id` deliberately not a FK — `:74-87`). Author-only RLS on all four rail tables (`:118-121`; SELECTs since rewritten to semijoin form, same semantics — `20260717100100:76-86`).
- **The extension doctrine is codified in-migration** (`20260701000000_structural_change_set_items.sql:10-13`): *extend `change_set_items` rather than add a sibling table* so realtime, RLS, pending fetches, and atomic reject keep working over one stream. It added `node_type ∈ ('block','lesson','module')` (closed CHECK — `:22-25`) + an identity constraint (`:28-41`), and mapped rename/move onto `op='update'` with detail in the snapshot (`:52-53`) — the precedent for carrying `matched/added/removed/split/merged` **in the item payload, never as new op values** ([R-5b](#r-5)).
- Accept is a status flip guarded on pending — **silent no-op on unknown/resolved ids** (`lib/ai/changeSet.ts:160-167`; preserve deliberately). Reject is all-or-nothing, compute-first (`:285-305`), aborts on failed/empty item reads (`:325, 335-336`), and is **hard-coupled to CourseDocument**: `inversePatches` throws on any unknown `node_type` (`:271`; missing `node_type` defaults to `"block"` — `:186, 200`), and `rejectChangeSet` unconditionally loads + reconciles the course doc (`:338-347`).
- Every DB access to the rail lives in `lib/ai/changeSet.ts` (grep: 9 hits, one module) — plus three read surfaces an extension must touch: the `studio_bundle` RPC's `pending_blocks`/`pending_nodes` arrays (`20260717100500:14-15, 82, 90`), the client-side Zod that hard-codes `node_type: z.enum(["module","lesson"])` (`lib/editor/studioLoad.ts:46` — a new node_type breaks the WHOLE bundle parse unless widened in lockstep), and the realtime INSERT sub filtered by course only (`lib/editor/useChangeSetRealtime.ts:28-33` — fires doc re-syncs that render nothing for graph items; a graph review surface needs its own consumer).
- Review UI: BlockFrame amber pending chrome resolves the whole set (`components/editor/BlockFrame.tsx:119-176`); EvidenceCard parses `{summary, severity, metrics, recommendation}` defensively (`EvidenceCard.tsx:27-34`); AgentPanel's review-bar groups come from the `change_set` **SSE event payload** (`structuralCount` — `AgentPanel.tsx:323-332`, `agentLoop.ts:394-426`), not DB rows — a graph group requires extending the event payload too. `AgentPlanHost` is the *wrong* pattern for extraction review (transient, never persisted — `AgentPlanHost.tsx:4-11`).

### 5.3 The honest extension plan (Wave 1 consumes this)

1. Migration in the exact `20260701000000` style: widen `node_type` CHECK with `'concept_graph'`, extend the identity constraint, store kind-tagged self-describing snapshots (the `StructureSnapshot` pattern — `changeSetDiff.ts:111-115`) with reconciliation classification inside the payload.

<a name="r-4"></a>
**R-4 · HIGH · Aggregate-only mastery (min cohort 5) inverts the platform's standing privacy posture.**
Creators today read individual progress, attempts, emails, flags, and raw event timelines (§10); `learner_flags` is author-only and learner-INvisible — the exact opposite shape. A creator can already triangulate a near-mastery picture from surfaces the directive doesn't remove.
*Resolution:* adopt the two-regime position explicitly: mastery, tutor threads, and tutor-derived inferences get the STRICTER regime (learner-own RLS, zero author policy, SQL-enforced cohort-5 aggregates); existing progress/attempt/roster surfaces keep today's posture; escalation dossiers pierce only via explicit learner consent. Document that the cohort floor bounds what the *tutor infers*, not what analytics already shows. If Henry instead wants legacy surfaces gated too, that's a much larger scope change (roster, learner detail, stuck queue) — decide now.

<a name="r-5"></a>
**R-5 · HIGH · The Accept/Reject rail cannot hold a concept-graph change-set without extension (accept-only today), and two vocabulary conflicts.**
(a) `inversePatches` throws on unknown `node_type` and `rejectChangeSet` unconditionally loads the course doc (§5.1) — un-extended, an extraction change-set would be **permanently un-rejectable**, weakening Accept/Reject (prohibited). Also `geometry.ts`'s layout is cycle-tolerant — DAG enforcement must live in the write path, never the renderer. (b) The directive's `matched/added/removed/split/merged` vocabulary conflicts with the closed `op ∈ create|update|delete` enum that revert ordering depends on.
*Resolution:* extend per the codified doctrine (§5.3): new `node_type` + domain revert branch + skip-doc-load + lockstep widening of the RPC/client-enum/event-payload surfaces; classification rides the item payload, `op` stays closed; `creator_locked` enforced in the diff. Extend `verify:reject` byte-for-byte.

<a name="r-6"></a>
**R-6 · HIGH · Learner tutor threads cannot reuse ANY existing conversation/message table.**
`conversations`/`messages` have no owner column and author-only RLS (§1.3, §10); `learner_messages` likewise. Piggybacking would expose learner threads to creators.
*Resolution:* net-new `tutor_threads`/`tutor_turns` (user_id NOT NULL, unique (user_id, course_id), learner-own RLS, service-role assistant writer, instructor-attributed member for escalation replies, idempotent on reply id) + an RLS-matrix int test asserting the author reads zero rows.

<a name="r-7"></a>
**R-7 · HIGH · "Deliver dossiers via the existing comms pipeline" — no creator-bound path exists.**
The pipeline is structurally learner-recipient-only end to end (§9); the notification bell is decorative; no digest/cadence infra exists anywhere.
*Resolution:* in-app escalation queue first (badge + inbox precedents); optional email digest via a NEW sanctioned `creatorDigest` seam reusing the comms *provider machinery* (fetch provider with Idempotency-Key + retry) under a documented amendment to the per-seam invariant, with creator opt-out + suppression checks and provider-mode surfaced in rows. Digest cadence rides the tutor settings row + the R-1 scheduler.

<a name="r-8"></a>
**R-8 · MEDIUM · "Live graded assessment items" have no referent — quizzes are low-stakes by explicit design.**
No scores/passing/timers/attempt caps anywhere in the content model (`types.ts:782-790`); unlimited attempts; per-attempt score/max_score IS recorded server-side for analytics. Answer-key leakage is already structurally impossible from anything the tutor can read (strict published schema + zero-policy keys table).
*Resolution:* redefine AC-T3.8's predicate deterministically: while the learner has a quiz block active (the new `quizActive` signal) the tutor scaffolds and never answers the on-screen question verbatim (question ids are resolvable from the snapshot the tutor already loads); charter `assessment_help` keeps its two values; drop "graded" language. The `[FWD]` certificate-lockout seam stays reserved.

<a name="r-9"></a>
**R-9 · MEDIUM · Cost telemetry "through the existing Zod event contract + security-definer ingest RPC" — the RPC is the wrong door for server-side calls.**
The RPC requires an authenticated session (`auth.uid()` pinned) + enrolled-or-author, and the platform's own authoritative server events deliberately bypass it via admin upsert (§3.3–3.4). Course-scoped cost rows are also author-readable under the select policy — a per-learner leak vector conflicting with R-4's regime.
*Resolution:* "existing contract" = the Zod union + `learning_events` table + serverEmit discipline, NOT the client RPC. Server-emit all tutor cost events (stable response-id-derived keys); protect learner attribution via a NULL course envelope (perf_vital pattern) or a `tutor_%` select-policy exclusion — tested in the RLS matrix; aggregates via a service-role-only view. State this in `docs/tutor/architecture.md` so nobody "fixes" the RPC.

<a name="r-10"></a>
**R-10 · MEDIUM · "Model ids from ONE config registry" is aspiration, not fact; gpt-5.6-* is unverified in this codebase.**
Config is split across `modelConfig.ts`, provider defaults, social env, marketing hardcodes; no gpt-5.6 literal exists; effort vocabularies per new model family are unknown (the `minimal`-rejection failure class is documented).
*Resolution:* `TUTOR_MODELS` job-type block in `modelConfig.ts` (the blessed registry), always passing model+effort per call; deny-list guard for `gpt-5.6-sol`; verify-suite grep banning tutor model literals elsewhere; a live smoke validating both model ids + accepted effort sets before Wave 3 hard-wires them. `runStructuredCall` gains `model/effort/timeoutMs/maxRetries` options first (§1.1).

<a name="r-11"></a>
**R-11 · MEDIUM · Embeddings/pgvector absent.**
Canonicalization + escalation clustering need vectors; whether the live Supabase tier can enable pgvector is unknowable from the repo, and migrations are currently applied by hand.
*Resolution:* `ModelClient.embed` via the existing openai dep (zero new deps) + deterministic mock; jsonb float arrays + in-process cosine at course scale (N≤200); column shaped for a later pgvector type change.

<a name="r-12"></a>
**R-12 · LOW · "snapshot_id" doesn't exist as an identifier.**
*Resolution:* define `snapshot_id ≡ course_publications.id` everywhere in TUTOR-1 (ambient context = `{course_id, publication_id, version, lesson_id, slide_id, position}`); key `snapshot_concept_map` PK `(publication_id, node_id)`.

<a name="r-13"></a>
**R-13 · MEDIUM · Slide ids are stable only while the draft slide object survives.**
Deck regeneration/delete+recreate mints new slide ids even for semantically identical content — slide-level anchors orphan; block ids are the durable row-id fallback.
*Resolution:* anchors store `{lessonId, blockId, slideId?}`; reconciliation re-resolves slide anchors per snapshot and downgrades to block-level when a slideId disappears (flagged, never silently dropped).

<a name="r-14"></a>
**R-14 · HIGH (for Wave 4) · "Persistent sidebar" contradicts the current learner architecture.**
No `[slug]`-level layout exists; both existing sidebars are page-mounted with un-persisted state; pages are force-dynamic; the only persisting layout has zero course context (§6). A page-mounted tutor silently loses its thread every lesson navigation.
*Resolution:* `app/(learn)/learn/[slug]/layout.tsx` hosts the sidebar (hard design decision, made now); Playwright asserts DOM/state survival across lesson→lesson navigation; module overviews mapped to the landing (no such route exists); `TutorPanel` on `/home` replaced in the same wave; sidebar gated on `isStudent`; ambient context via a new zod-free learner store fed by `onSlideChange`/video/imported-deck taps.
